# Should VTSearch force safe thresholds on? (issue #2799)

_An Autopilot simulation study on the HLTCOE Grid, run on a fresh `dev` worktree
(`claude/safe-thresholds-2799`). Every number below is generated by
`scripts/experiments/calibration/analyze_ab.py` and `analyze_safe.py` from the
per-cell CSVs; the prose is written on top of those numbers._

**Status: DRAFT — the Grid run is in flight; the numbered sections are filled in
from the analyzers' output when it lands.**

## The question

`safe_thresholds` blends the cross-calibration (conformal) threshold with a GMM
threshold fitted on the current score distribution
(`vtscore.training.thresholds.calculate_safe_threshold`). The blend has **full**
authority below 6 votes and majority authority up to ~13. Issue #2799 asks
whether it should be **on for every VTSearch user** — so this study measures it
on the head the app actually ships, and as a deployment A/B rather than a
threshold-rule comparison.

Two things make that non-trivial, and both are why this is a fresh study rather
than a re-read of #2781:

1. **The head.** The #2781 calibration study (and the cached `safe_thresholds
   False` cells it produced) ran the harness's historical auto-sized **MLP**.
   Production has trained a **linear (logistic) head** since #2790/#2809. Pairing
   new safe-ON cells against those cached safe-OFF cells would confound the blend
   with the head swap, so both arms here are re-run at `head=linear`
   (`simulate_voting_iterations(head=...)`, new in this branch, threads
   `LINEAR_HEAD` into the final fit *and* the calibration folds — the same
   single-width discipline production uses in `_train_and_score_xy`).

2. **The threshold is not output-only.** Autopilot's Hard phase picks the
   unlabeled item nearest the decision threshold
   (`al_strategies._hard_pick_by_index`), so turning the blend on changes *which
   items the user is asked to vote on*. A within-step counterfactual — every GMM
   variant re-cutting one model, which is what `analyze_safe.py` measures — is
   blind to that feedback. The ship decision therefore reads a **trajectory
   A/B**: two full runs, `safe_thresholds` on and off, paired per
   **(arm, category, seed) cell**, because the runs' label sets diverge and steps
   are no longer comparable across arms.

## Design

| | |
|---|---|
| Dataset | `visual_genome_m`, region voting (ground-truth boxes) |
| Primary arm | `dinov3_patch` × `max_patch` — the production region-vote strategy |
| Control arm | `siglip` × `whole_image` — single-vector, isolates the blend from region max-pooling |
| Head | `linear` (production, #2790/#2809) on both arms |
| Steps | 30 voting steps (above ~20 votes the blend is pure cross-cal) |
| Seeds | 12 |
| Categories | 24 per embedder, scale-band selection shared with the Max-Patch/#2781 studies |
| Cells | 552 per arm × 2 arms |
| Fixed | inclusion 0, `sim_fraction` 0.5, `calibrate_count` 2, `calibration_fraction` 0.5, `autopilot_fidelity=True` |

Deviations from the pre-registered plan
(`docs/plans/safe-threshold-gmm-experiment.md`), both recorded before the run:

* **12 seeds instead of 8.** The plan sized seeds for a single safe-ON run; the
  A/B needs cell-level power on *two* runs, and a linear-head cell turned out to
  cost 188 s on CPU, so the extra seeds were nearly free.
* **The trainer is the production head, not the MLP** — the plan's "MLP trainer"
  line predates #2809 (see "The question" above).
* **The inclusion-budget sweep is reduced to one k.** That sweep answers #2781's
  question, not this one, and `/exp` is a shared 50 GB volume.

### Windows, and which of them a user can see

Vote count `n = n_good + n_bad`, the unit the blend's own ramp is keyed on:
**2–5** (pure GMM, blend weight 0), **6–20** (the ramp), **21+** (pure
cross-cal). Cutting across those, the analyzer splits every comparison by
**scope**: `app_visible` keeps only steps where the app would have had a trained
detector on screen (`app_trained`), `all_steps` keeps every trainable step.
That distinction is load-bearing here — see §Results.

## Reproducing

```bash
# Grid worktree with this branch at /exp/$USER/projects/vts-safe2799
cd /exp/$USER/projects/vts-safe2799/scripts/experiments/calibration
bash launch_safe_ab.sh          # prepare -> ON + OFF arrays -> analyze_safe + analyze_ab
```

`VTS_REPO` must point at the worktree: `common.setup_env()` puts it at the front
of `sys.path`, so without it the tasks import `vtscore` from whichever worktree
the default names.
