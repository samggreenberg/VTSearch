# Long-running-op observability — 2026-05-28

Task 4 of [docs/plans/browser-vision-testing.md](../plans/browser-vision-testing.md).
Driven via the Playwright MCP browser at 1440×900, light theme. Server
was started against an empty `data/` (existing `data/` moved aside;
embedder models + synthetic generator cache symlinked back in so the
"first" import wouldn't have to re-download SigLIP). Because the
SigLIP weights were cache-warm on the host, the "cold embedder load"
phase the plan calls for did not actually fire in this session — the
imports started straight at the per-file embedding stage. The
embed-files stage itself is still slow (~10–20 seconds per item-batch
on CPU), so the progress UX still got a real workout.

Findings tagged `O#` (observability). Severities are Low / Med / High.

## Op 1 — First demo import (Synthetic, size = 100, cache-warm SigLIP)

**Wall-clock**: ~5 min start to finish.

**Sequence observed**:

- 0% (screenshot taken after click + a few seconds): the row was already
  at "Loading dataset · embedding files (32/100)" with a partial blue
  progress bar and a Cancel button (`01-op1-0pct.png`). The plan's
  "Loading SigLIP weights · First-time only" sub-status was not visible
  at all — the model was already in cache, so the loader skipped
  straight to embedding. This is the *correct* behavior for the
  cache-warm case (and resolves the misleading-copy concern raised as
  O2 in the edge-states audit).
- ~50% (`02-op1-50pct.png`): same row layout, progress bar advanced.
- Late (~96%): `04-op1-still.png` — progress bar near full, sub-status
  "(96/100) Embedding SigLIP 96/100…", and an inline ETA "~42s left"
  rendered just before the Cancel button. This is where the first
  finding fires.
- Done (`05-op1-done.png`): row collapses to ds-A | Image | 100 |
  2026-05-28 05:39 | Loaded ✓ | action buttons. Train CTA enables at
  the bottom.

### Findings — Op 1

- **O3 (Med) — "Time remaining" ETA disagrees with the visual progress
  bar near the end.** At 96/100 the bar visually showed ~95% complete
  but the inline ETA read "~42s left", implying ~10s/item for the last
  4 items — at a sustained pace that wouldn't match the prior rate
  (the first 32 items completed in roughly 60s of total elapsed time
  from the user's POV). Likely the ETA is computed from a moving
  average that's stale, or there's a follow-on phase (e.g. registry
  save, see Op 2) that the ETA accounts for but the per-item bar
  doesn't. Either fix the ETA math or split the bar into the two
  phases.
  Screenshot: `04-op1-still.png`.

- **O4 (Low) — Progress sub-status shows the count twice: "(96/100)
  Embedding SigLIP 96/100…".** Once in the parenthesized prefix, once
  in the SigLIP message. Cosmetic redundancy.
  Screenshot: `04-op1-still.png`.

- **Positive — header / sub-status / bar / cancel pattern is clean.**
  Two-line status (`Loading dataset · embedding files` + the per-item
  detail line) plus a determinate progress bar plus a visible Cancel
  is the right structural shape for a long op.

## Op 2 — Warm re-import (Synthetic, size = 50)

**Wall-clock**: ~3 min (still slow because the per-item embed work is
the same; only the SigLIP cold-load is saved, which was already free
on this host).

**Sequence observed**:

- Mid-progress (`06-op2-warm-start.png`): "Loading dataset · embedding
  files (32/50) Embedding SigLIP 32/50…" — same layout as Op 1, no
  visible difference even though this is the "warm" case. The user
  cannot tell from the UI whether this is a cold or warm SigLIP load.
- A NEW phase appeared briefly after embedding completed: **"Loading
  dataset · saving to registry"** (`07-op2-saving-registry-phase.png`).
  This phase was visible for only a second or two but flashed onto
  the screen and is captured in the screenshot.

### Findings — Op 2

- **O5 (Low) — The "saving to registry" sub-phase appears with no
  preceding signal it's coming, and disappears within ~1 second.**
  For most users it'll just be a brief flicker; for users on a very
  slow disk it could last longer and be confusing because the row
  has no embed count to show, only the phase name. Suggested fix:
  render the phase in the same two-line shape (header + sub-status)
  with sub-status text like "writing dataset.pkl…" so the user knows
  the work is real and not a UI hiccup.
  Screenshot: `07-op2-saving-registry-phase.png`.

- **O2 (Low, related) — Warm vs cold path is indistinguishable to the
  user.** Since the only "first-time" copy is on the SigLIP weights
  load and that's been skipped in both runs here, the user has no
  signal that they should expect a re-import to be faster than a
  first import. A small "(SigLIP cache hit)" subtitle on the first
  visible second of the warm case would set expectation.

## Op 3 — Train + re-rank cycle

Created a `smiley` detector, then voted on ~10 items via the
autopilot (rapid alternating ← / → keypresses).

**Sequence observed**:

- Each vote landed the next image essentially instantly (sub-1s in
  the steady state). No "training…" spinner, no progress bar, no
  "re-ranking…" indicator at any point.
- After 10 votes (`15-op3-mid-voting.png`), the autopilot sidebar
  had ticked off "Find Initial Goods" (✓) and "Find Initial Bads"
  (✓) and landed on "Refine Boundary · 10 labels" with two warning
  dot indicators next to the count.
- Back on the dashboard (`16-op3-after-train.png`), the detector row
  picked up `# Training = 10`, `Last Trained = <time>`, `Loaded ✓`.

### Findings — Op 3

- **O6 (Low) — Train + re-rank is invisible by design.** For
  fast cycles (CPU laptop, small dataset) this is the right call —
  a spinner that pops in and out per vote would be noise. But for a
  slow re-rank (large dataset, or constrained host) the user would
  see a delay between voting and the next image, with no indication
  that "the model is updating with your vote." Suggested fix:
  introduce a very small lower-rail badge (e.g. "training…" pill)
  that only appears when the rerank exceeds some threshold
  (e.g. 500 ms), so fast cycles stay silent and slow cycles get
  feedback.

- **O7 (Low) — The autopilot stage list uses warning-coloured dots
  ("⚠️⚠️") next to "Refine Boundary · 10 labels" with no tooltip
  or legend explaining what the dots mean.** Without context, the
  warning colour reads as "something's wrong with the labels," but
  the model appears to be progressing normally. Either drop the
  dots, change their colour to neutral, or add a tooltip ("two
  items in this stage still need attention").
  Screenshot: `15-op3-mid-voting.png`.

## Op 4 — Concurrent imports

Started an import (`ds-C-concurrent-1`, size 100) and then immediately
clicked the `+` button on the Datasets section to queue a second one.

**Result**: the `+` button is **disabled** while any import is in
flight (`09-op4-import-disabled.png`). The dashboard does not allow a
second import to be initiated at all; the user has to wait for the
first one to finish before they can even open the Add Dataset modal.

### Findings — Op 4

- **O8 (High) — The concurrent-import behavior described in
  CLAUDE.md cannot actually be exercised from the dashboard.**
  CLAUDE.md describes `_download_gate` and `_embed_gate` allowing a
  second import to download while the first embeds. The dashboard's
  `+` button is hard-disabled while any import is running, so the
  user can't reach that path through the UI. Either the gates only
  exist on the API/CLI surface (and the UI imposes its own
  serial-only constraint), or the gates have been removed but
  CLAUDE.md hasn't caught up. Worth confirming in `vtsearch/routes`
  and reconciling the documentation.
  Screenshot: `09-op4-import-disabled.png`.

- **O9 (Med, related) — The disabled `+` button has no tooltip
  explaining why.** A user who wants to queue work sees "import is
  greyed out" with no hint that it's because another import is
  running. A `title="Wait for the current import to finish before
  starting another"` would close the gap.

- **O10 (Med) — Existing dataset rows (not the in-progress one) all
  have their action buttons greyed out as well during an import.**
  In `09-op4-import-disabled.png`, ds-A's rename / stats / delete
  action icons are grey and the row checkbox is unselectable. A
  user can't rename or delete an *unrelated* dataset while a
  separate import is running. If this is a necessary lock (e.g.
  registry-write serialization), the rows should at least have
  visual / tooltip feedback explaining why — currently they just
  look broken.

## Op 5 — Cancel mid-load

Started a 200-item synthetic import, waited until the row was at
32/200 (`11-op5-before-cancel.png`), then clicked Cancel.

**Sequence observed**:

- T+0 (clicked Cancel).
- T+3s (`12-op5-after-cancel.png`): row still shows the same
  "Loading dataset · embedding files (32/200) Embedding SigLIP
  32/200…" sub-status, the bar is at the same fill, and the Cancel
  button is still rendered. The UI looks identical to pre-cancel
  except that the active checkbox has hopped to a different row.
- T+8s (`13-op5-cancelled.png`): same — bar still at 32/200, Cancel
  button still there.
- T+~20s (`14-op5-15s-after-cancel.png`): the in-progress row is
  gone. The remaining datasets (ds-A, ds-B-rewarm, ds-C-concurrent-1)
  are normal. No partial dataset registered, no error toast, no
  orphan files.

### Findings — Op 5

- **O11 (High) — Cancel works correctly but provides zero feedback
  for ~15–20 seconds.** After clicking Cancel, the progress row
  freezes in its pre-cancel state (same bar fill, same sub-status,
  same Cancel button) until the cleanup completes. A user would
  reasonably assume the click was lost and click Cancel again, or
  switch to a different action. Suggested fix: as soon as Cancel
  is clicked, change the sub-status to "cancelling…" and either
  replace Cancel with a disabled "Cancelling…" badge or remove it.
  Screenshots: `12-op5-after-cancel.png` (T+3s), `13-op5-cancelled.png`
  (T+8s).

- **Positive — the cleanup itself is correct.** When the row
  disappears, no orphaned partial dataset is left in the registry,
  no error toast fires, and the surrounding rows are unaffected.

## Patterns

- **Progress phases are not declared up front.** The user sees
  `embedding files` then `saving to registry` as the operation
  progresses, with each new phase appearing mid-row with no
  preceding hint. A small "expected phases" indicator (or a
  multi-segment progress bar) would make the long op feel less
  improvised. This shows up most clearly in Op 2's brief
  "saving to registry" flash.

- **Cancel has no acknowledgement state.** Op 5 shows the worst
  case (~20s of frozen UI between the click and the row
  disappearing). Adding a "cancelling…" sub-status would close
  that gap without any backend change.

- **Disabled controls don't say why.** Op 4 (the `+` button while
  an import is in flight), Op 4 (unrelated dataset rows greyed
  out), and the e2e-flows audit's U6 (new-detector Create button
  with empty examples) all share the same antipattern: a primary
  affordance disables silently. A repo-wide rule "if a button is
  disabled, give it a `title` explaining why" would unify this.

- **Fast operations are silent and that's mostly fine.** Op 3
  (train+rerank per vote) and Op 6 (autodetect on 100 items) both
  complete in well under a second and skip any progress UI. That's
  the right default; the issue is only at the long-op tail (slow
  hosts, large datasets) where the same code path provides no
  fallback feedback.

## Concurrency-gate behavior

CLAUDE.md describes `_download_gate` and `_embed_gate` permitting a
second import to download while the first embeds, with default 1/1
limits preventing concurrent embedding. **The dashboard does not
expose this behavior**: the `+` Import button is disabled the
instant any import row goes into progress, so a second import can't
be initiated from the UI at all (Op 4, finding O8). This means:

- Either the gates exist only on the API/CLI path, and the UI has
  layered its own stricter serialization on top.
- Or the gates have been removed and CLAUDE.md is stale.

Either way, a user reading CLAUDE.md and trying to verify the
behavior through the dashboard will conclude the docs are wrong.
Worth a follow-up: grep `_download_gate` / `_embed_gate` in
`vtsearch/`, confirm the actual current state, and update either
the dashboard or the docs (or both — ideally let the UI queue a
second import if the API supports it).
