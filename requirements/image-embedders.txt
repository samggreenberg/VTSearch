# VTSearch: All image embedders
#
# Image-only deployment that ships every supported image embedder:
#   * SigLIP   (google/siglip-base-patch16-224)         - default, text-capable, ungated
#   * SigLIP 2 (google/siglip2-base-patch16-224)        - text-capable, ungated
#   * SigLIP2-L (google/siglip2-so400m-patch14-384)     - text-capable, ungated, 1152-d
#   * SigLIP-L (open_clip ViT-SO400M-14-SigLIP-384)     - text-capable, ungated, 1152-d
#   * CLIP     (openai/clip-vit-base-patch32)           - text-capable, ungated
#   * DINOv2   (facebook/dinov2-base)                   - image-only, ungated
#   * DINOv3   (facebook/dinov3-vitb16-pretrain-lvd1689m) - image-only, gated
#   * EUPE     (facebookresearch/EUPE, ViT-B/16)        - image-only, ungated
#
# Used by BOTH docker/Dockerfile.image-embedders (CPU) and
# docker/Dockerfile.image-embedders.gpu (CUDA). There is deliberately no
# `-gpu` twin of this file: the CPU and GPU dependency sets are identical
# package-for-package, and the *only* thing that differed was which PyTorch
# wheel index to resolve `torch` / `torchvision` from. That is an install-time
# concern, so each Dockerfile passes its own `--extra-index-url` (the same
# split requirements/gpu.txt already uses), and this list stays index-agnostic.
#
# Installing it by hand therefore resolves torch from PyPI (the CUDA build).
# For a CPU-only environment, spell the index the CPU image uses:
#
#   pip install --extra-index-url https://download.pytorch.org/whl/cpu \
#               --prefer-binary -r requirements/image-embedders.txt
#
# Skips audio / video / text / document stacks so we still produce a slim
# image (only image-side deps are pulled in).

# SigLIP 2 + DINOv3 require recent transformers ( >= 4.49 ships SigLIP 2,
# and DINOv3's HF wrapper landed in the same window ). Pin a known-good
# floor instead of "latest" so the image is reproducible.
#
# The floor deliberately stays at 4.49 even though the *default image-processor
# backend flips inside this range*: transformers 5 removed the `Fast` suffix, so
# the bare `SiglipImageProcessor` means the PIL implementation below 5 and the
# torchvision one at 5+, and the two disagree on 53-59% of pixel elements
# (#3146). Raising the floor to >=5 is not the fix, because it only governs what
# *installs*. Since #3173 the app names the backend outright
# (`VTSEARCH_IMAGE_PROCESSOR_BACKEND`, default `torchvision`), and the request is
# spelled for whichever version is present (`backend=` on 5, `use_fast=` on
# 4.x) — so both sides of this range now resize identically, which is the
# property a floor could never give us in someone's existing environment.
transformers>=4.49.0
pandas

# ── VTSBrowse projection ─────────────────────────────────────────────
# The Browse canvas fits UMAP on the embedding matrix (vtscore.gpu_backends
# .umap_fit_transform, imported lazily). Needed by every deployment
# regardless of media type: nothing else pulls umap-learn in transitively,
# so omitting it leaves Browse broken at runtime rather than at build time.
# Neither image ships cuML, so the CPU umap-learn path is the only one.
umap-learn

# ── PyTorch (index chosen by the caller; see the header) ─────────────
torch>=2.0.0
# Every image embedder now asks for the torchvision image-processor
# backend by name rather than inheriting a default (#3173), so torchvision
# is a hard requirement of the preprocessing path and not just of DINOv2 /
# DINOv3's `AutoImageProcessor`. Without it the processor import raises
# ImportError at build time. Listed here rather than installed separately
# so it resolves from the same wheel index as `torch` above and the two
# builds always match.
torchvision
